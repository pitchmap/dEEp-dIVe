## 안건 1. 동시 착수 대 순차 착수 — "네 명이면 세 스프린트를 병렬로 돌 수 있지 않나"

**남유리:** *(발의)* "착수 전에 짚고 싶습니다. 우리는 4인이고 스프린트는 A·B·C 셋입니다. 산술적으로는 인원을 나눠서 **A·B·C를 동시에 시작**하면 전체 기간이 줄어요. 제가 B의 선박 시각 구분을, 세진 님이 C의 탐지를 미리 파는 식으로. 순차 게이트는 '완료 판정'의 순서지 '착수'의 순서까지 강제해야 합니까?"

**정하늘:** *(강한 반대)* "착수의 순서까지 강제해야 합니다. 이유는 하나 — **A·B·C를 동시에 시작하면 계약이 계속 변합니다.** 구체적으로 세 장면을 그려보죠.

**장면 1.** 세진 님이 C의 탐지 시스템을 구현하는 중에, A에서 조준 심도 제한과 카메라 구조가 바뀝니다 — 실제로 지난주에 바뀌었죠. 그 순간 탐지·조준·경고 UI의 연결을 전부 다시 해야 합니다. C가 A의 미확정 계약 위에 서 있었으니까요.

**장면 2.** 유리 님이 B에서 경비함을 만들었는데, C의 추적 상태 계약이 나중에 변경됩니다 — 추적 진입 조건이나 상태 이벤트 이름이 바뀌면 경비함 AI도 다시 고쳐야 합니다. 경비함은 추적 계약의 소비자니까요.

**장면 3.** A에서 아직 가격과 구매 UI가 확정되지 않았는데 B의 고가치 수송선 보상을 만들면 — 무엇이 '고가치'인지 **기준 자체가 없습니다.** 크레딧 100이 큰돈인지 푼돈인지는 A의 경제 데이터가 정의하는 겁니다.

결과는 우리가 7차 대회의에서 이름 붙인 그 상태예요 — **모든 기능이 조금씩 구현되지만 어느 것도 완성되지 않는 상태.** 병렬은 인원의 병렬이어야지 스프린트의 병렬이면 안 됩니다. 4인의 병렬성은 A **안에서** 씁니다 — A를 네 조각으로 나눠 동시에 파는 거죠. 그게 안건 2입니다."

**오세진:** "장면 1의 당사자로서 증언 — 조준 계약이 확정 전이었으면 저는 지난주에 탐지 코드를 두 번 짰을 겁니다. 순차 착수 찬성."

**남유리:** "…계약 소비자 논리는 반박이 안 되네요. 철회합니다. 한 가지만 확인 — 아트 에셋(선박 색·실루엣 시안)은 도윤 님·세라 님 영역이라 개발 창 밖이니, 그쪽 선행 작업까지 막는 건 아니죠?"

**정하늘:** "아닙니다. 금지되는 건 **개발 창에 A 범위 밖 작업을 입력하는 것**입니다. 기획·아트의 선행 준비는 오히려 B 착수를 빠르게 하니 환영이에요. 경계는 명확히 — 에셋은 준비하되, 그걸 게임에 붙이는 코드는 B 착수 전에 존재하면 안 됩니다. 스텁 금지 원칙 그대로."

> **결의 1:** **스프린트 병렬 착수 기각, A 단독 착수 확정.** 근거: 미확정 계약 위의 선행 구현은 재작업을 낳는다(조준→탐지 / 추적→경비함 / 경제→고가치 기준의 3중 의존). 4인의 병렬성은 스프린트 간이 아니라 **A 내부의 창 분할**로 사용한다. 아트·기획의 B 선행 준비는 허용하되, 개발 창의 A 범위 밖 코드 작업은 금지(스텁 금지 준용).

## 안건 3. 병합 순서와 통합 규칙 — 계약 생산자부터, 검증자는 마지막에

**남유리:** *(질의 1건)* "병합 순서 '리드 → 게임플레이 → 그래픽스 → 툴링'의 근거를 묻습니다. 특히 왜 그래픽스가 게임플레이 뒤입니까? 조준 시점·레이어 작업은 게임플레이와 독립적으로도 돌아가는데요."

**정하늘:** "순서의 원리는 **의존 방향**입니다.

1. **리드 먼저** — 계약(앵커·소켓·인터페이스)의 생산자. 이게 dev에 없으면 나머지 셋은 병합 시점에 계약 불일치가 터집니다.
2. **게임플레이 둘째** — 판정과 상태의 생산자. 조준 상태, 구매 결과, 장착 상태가 여기서 나옵니다.
3. **그래픽스 셋째** — 유리 님 창은 독립적으로 '돌아가긴' 하지만, UI는 **판정의 소비자**입니다. 구매 불가 사유 5종을 표시하려면 판정이 먼저 dev에 있어야 하고, 조준 시점은 소켓 계약 위에, 피드백 UI는 트랜잭션 결과 위에 섭니다. 소비자가 생산자보다 먼저 병합되면 임시 목업에 연결했다가 다시 배선하는 이중 작업이 나요.
4. **툴링 마지막** — 검증은 **모든 코드가 모인 위에서** 돌아야 의미가 있습니다. A1~A8 자동 검증이 리드·게임플레이·그래픽스가 없는 dev에서 돌면 전부 빨간불이거나, 더 나쁘게는 비어 있는 코드에 맞춘 가짜 초록불이 됩니다."

**남유리:** "생산자→소비자→검증자 순이라는 원리면 납득합니다. 철회."

**오세진:** "통과 판정 절차도 못 박죠. 각 창이 '내 창에서는 된다'로 끝나면 안 되고 —"

**임찬영:** "제가 규격을 냅니다.

1. 네 창의 feat 브랜치가 순서대로 dev에 병합 완료
2. 통합 창이 **dev의 실제 빌드**에서 A1~A8을 검증 — 각 창의 로컬 확인은 참고, 판정은 통합 빌드에서만
3. A5는 보완분 결의 7대로 **A5-T1~T6 저장 실패 롤백 시나리오까지 포함**해야 통과
4. 전 항목 통과 시 **통합 PR**(dev → main) 생성, 리드 승인으로 병합 — 이게 스프린트 A의 공식 종료
5. 그 전까지 **B 브랜치는 존재해도 병합 금지** — B 착수 허가는 A 통합 PR 병합이 유일한 방아쇠"

**서지우 (배석 발언):** "기획 접점 — A 통합 PR이 병합되는 시점이 7차 대회의가 정한 '스프린트 A 종료 리뷰'의 소집 조건입니다. 지참물(A1~A8 검증 기록, 경제 params 커밋 이력, 시뮬레이터 비용 곡선, 조준 규격 준수 영상)은 통합 빌드 기준으로 준비해주세요."

> **결의 3:** 병합 순서 **리드 → 게임플레이 → 그래픽스 → 툴링** 확정(생산자→소비자→검증자 원리). 통과 판정은 각 창 로컬이 아닌 **dev 통합 빌드의 A1~A8 검증**으로만, A5는 A5-T1~T6 포함. 전 항목 통과 시 통합 PR 생성이 스프린트 A의 공식 종료이며, **그 전까지 B 브랜치 병합 금지**(B 착수 방아쇠 = A 통합 PR 병합).

## 안건 4. 전체 로드맵 — 4단계 확정

**정하늘:** "마지막으로, A 너머의 순서를 실행 선언으로 봉인합니다. 13차 결의 1의 2단계 게이트 구조를 실행 언어로 번역한 겁니다.

### 1단계: 스프린트 A
> **목표: 전 심도 조준과 성장 UI를 실제 사용 가능한 상태로 완성한다.**
- 5창 전부 A 범위만 입력 (본 회의 체제)
- A1~A8 전부 통과 후 통합 PR

### 2단계: 스프린트 B 핵심
> **목표: 공격할 배와 공격하지 말아야 할 배를 구분하고, 잘못 공격하면 실제 경비함이 출현한다.**
- B1~B5 통과 시 C 작업 착수 가능
- **B6 보상 튜닝과 B7 오인율 측정은 C와 병렬로 계속** (13차 결의 1의 최종 종료 조건)

### 3단계: 스프린트 C
> **목표: 플레이어가 탐지되고, 추적당하고, 폭뢰에 맞고, 침수되며, 파괴될 수 있게 만든다.**
- C1~C9 전부 통과하면 **보스 AI 본개발 시작** (C9 = 전투 임시값 이관, [COMBAT] 태그)

### 4단계: 잔여 작업
- B6 고가치 수송선 보상 최종 튜닝
- B7 오인 사격률 테스트 (보완분 결의 10의 계산식·표본 규격 적용)
- 어뢰 추적 카메라
- 중립 선박 고유 사운드
- 실패 화면 고급 연출

어뢰 캠은 7차 결의대로 **A~C 이후 남는 시간에만** 작업합니다. 4단계는 보스 본개발과 병렬이며, '게이트 제외 ≠ 제작 면제' 원칙에 따라 스프린트 완료 선언에는 전부 필요합니다."

**오세진:** "각 단계 전환 시에도 오늘 방식 그대로죠? B 착수 때 5창의 범위표를 B 범위로 갈아끼우는 소회의를 다시 여는 걸로."

**정하늘:** "그렇습니다. 범위표 교체는 회의체 결의 사항 — 창의 방화벽은 창 주인이 아니라 회의가 옮깁니다."

> **결의 4:** 4단계 로드맵 확정 — **A(전 심도 조준·성장 UI 완성, A1~A8+통합 PR) → B 핵심(적대·중립 구분과 경비함 실출현, B1~B5, B6·B7은 병렬 지속) → C(탐지·추적·폭뢰·침수·파괴 성립, C1~C9 통과 시 보스 본개발) → 잔여(B6·B7·어뢰 캠·고유 사운드·고급 연출, 보스와 병렬).** 어뢰 캠은 A~C 이후 잔여 시간 한정. 단계 전환 시 창 범위표 교체는 소회의 결의로만 수행.

## 총괄 — 실행 선언

| 항목 | 결정 |
|---|---|
| 착수 방식 | A 단독 착수, 스프린트 병렬 기각(계약 변동 3중 의존 근거), 병렬성은 A 내부 창 분할로 |
| 작업 창 | 5창 체제(리드/게임플레이/그래픽스/빌드·툴/통합), 창에는 A 범위만, 범위 고정 규칙 |
| 통합 창 | 리드 겸임 + 코드 작성 금지 + 리드 창 병합은 교차 승인 |
| 병합 | 리드→게임플레이→그래픽스→툴링, 판정은 dev 통합 빌드 A1~A8(A5는 T1~T6 포함), 통합 PR = A 종료 |
| B 통제 | A 통합 PR 병합 전 B 브랜치 병합 금지 |
| 로드맵 | A → B 핵심(B6·B7 병렬) → C(C1~C9 → 보스 본개발) → 잔여 5종, 어뢰 캠은 A~C 후 잔여 시간 |

**서명:** 개발팀 4인 전원 합의
(스프린트 병렬 착수안 철회 1건 — 계약 소비자 논리 / 통합 창 겸임 이의 1건 — 교차 승인 절충 / 병합 순서 질의 1건 — 생산자→소비자→검증자 원리로 해소)

**차기:** A 통합 PR 병합 시 — ① 스프린트 A 종료 리뷰(대회의, 지참물은 통합 빌드 기준) ② B 범위표 교체 소회의 연속 개최
