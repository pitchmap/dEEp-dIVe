## 안건 1. 수중 조준과 선수 조준 카메라 — 방향이 아니라 규격까지

### 1-1. 방향 결정

**박태현:** "판정은 단순합니다. 6차에서 우리는 **수중 보스와 싸우는 게임**이 됐어요. 보스도, 해저 보물도, 소형 수중 적도 물속에 있는데 조준이 수면에서만 되면 신규 콘텐츠 전부가 조준 불가 지역에 사는 겁니다. 자동 부상은 더 나쁩니다 — 심도는 생존 자원인데 조준이라는 기본 행동이 그걸 멋대로 소모해요. 은신하러 내려갔다가 쏘려는 순간 떠올라 발각되는 구조입니다."

**김세라:** *(강한 반대)* "기능 논리는 맞는데, 이 수정이 뭘 죽이는지는 알고 갑시다. 5차에서 조준경이 채택된 명분은 **'잠망경 부활 1순위' 조건의 이행**이었어요. 선수 발사관 시점이 되는 순간 그건 잠망경이 아니라 줌 버튼입니다. 기능을 위해 정체성을 파는 결정에 반대합니다."

**이준호:** "세라 님, 그 폐쇄감을 만든 게 잠망경이라는 '단어'입니까, 아니면 원형으로 좁아지는 시야·가라앉는 BGM·소나 핑과 심장박동이라는 '감각'입니까? 후자라면 전부 이식됩니다. 게다가 수중 조준이 되면 심도별 표정이 생겨요 — 얕은 조준엔 수면의 찰랑임, 깊은 조준엔 압력의 저음만."

**김세라:** "…감각의 목록으로 반박당하면 할 말이 없죠. 조건부 철회 — 첫째, 원형 마스크·비네트·FOV 축소·덕킹은 **조준경 불가침 요소**로 명문화. 둘째, 인게임 명칭을 '어뢰 조준경'으로 정리하고 관측용 잠망경은 백로그 분리 보존, 부활 조건은 '수면 정찰이 게임플레이로 필요해지는 시점'."

### 1-2. 카메라 규격 확정 — "선수에서 조준한다"만으로는 두 개의 구현이 나온다

**정하늘:** "여기서 초안 회의가 멈췄던 지점을 넘어갑니다. '선수 발사관에서 조준'은 방향이지 규격이 아닙니다. 이대로 개발에 넘기면 카메라 오프셋과 어뢰 생성 오프셋을 각자 계산하다가 **조준선과 실제 탄도가 어긋나는** — 축 규약 사태의 재림이 옵니다. 오늘 일곱 개를 못 박습니다.

**① 단일 앵커 원칙.** 잠수함 모델에 `torpedoTubeAnchor` 명시적 앵커 1개를 둡니다. **조준 카메라 위치와 어뢰 생성 위치가 이 앵커의 동일 좌표계를 공유**합니다. 각자 오프셋 계산 금지 — 이건 규격이 아니라 금지 조항입니다.

**② 카메라 위치.** 앵커 정위치. 잠수함 중심에서 앞으로 떨어진 별도 오프셋을 두지 않습니다.

**③ 자기 선체 처리.** 조준 중 잠수함 자기 모델은 **렌더 제외.** 카메라가 선체 최전방 밖에 있으므로 모델 내부 클리핑이 원천 차단되고, 벽·선박에 선수를 붙인 상태에서도 카메라가 오브젝트 안으로 들어갈 일이 없습니다."

**한도윤:** *(이의 1건)* "③에 이의 — 1인칭에서 자기 배가 하나도 안 보이면 '내가 잠수함이다'라는 감각이 끊깁니다. 프레임 하단에 선수 일부라도 걸치게 하면 방향감도 살고요."

**김세라:** "그건 모델이 아니라 **조준경 UI로** 해결합시다. 마스크 하단에 발사관 튜브 프레임을 2D로 그려 넣으면 — 실제 어뢰 발사관에서 내다보는 그림이 됩니다. 3D 선수를 걸치면 클리핑 문제가 되돌아오지만, 2D 프레임은 공짜예요. 폐쇄감 연출로는 오히려 이쪽이 강합니다."

**한도윤:** "2D 튜브 프레임이면 철회합니다. 제가 그리죠."

**정하늘:** "채택. 계속 —

**④ 조준-탄도 일치.** 어뢰 초기 진행 방향 = 조준 카메라 시선 방향. 완전 동일. 십자선이 곧 탄도입니다(리드샷 보조선은 그 위에 표시).

**⑤ 조준 중 기동.** 허용 여부를 결정해야 합니다."

**박태현:** "**허용**을 주장합니다. 이동하면서 각을 잡는 게 리드샷 손맛의 절반이에요. W/S 전후진, Ctrl/Shift 심도 유지, A/D 선회 시 조준선도 선체와 함께 돌아갑니다. 조준 중 정지를 강제하면 조준 = 무방비 시간이 돼서, 어뢰 캠에서 걱정했던 문제를 조준 단계로 옮겨올 뿐입니다."

**정하늘:** "허용 채택. 마우스는 발사관의 미세 조준각(제한된 콘 범위), 선체 선회는 A/D — 큰 각은 배를 돌리고 작은 각은 마우스로. 마지막 —

**⑥ 발사 후 카메라.** 자동 해제하지 않고 **조준경 유지.** 연속 사격 흐름을 끊지 않기 위해서입니다. 해제는 기존대로 우클릭, 어뢰 시점 전환은 안건 2의 어뢰 캠 키로만.

**⑦ 문서 회귀 방지.** 가장 중요한 항목일 수 있습니다. 현재 프로젝트 상태 문서와 테스트 체크리스트에 **'잠망경 심도 전용 조준'이 확정 규약으로 남아 있습니다.** 코드만 고치면 다음 통합 때 누군가 문서를 근거로 옛 동작을 복원하는 — 문서발 회귀가 납니다. 오늘 결의로 해당 규칙을 상태 문서·체크리스트·conventions에서 **삭제**하고, 원칙을 추가합니다: **결의로 사양이 변경되면 코드와 상태 문서를 같은 작업 단위에서 동시 갱신한다. 문서 미갱신 = 작업 미완료.**"

**서지우:** "⑦은 회의체 운영 원칙으로 승격해서 받겠습니다. 회의록과 상태 문서가 어긋나면 회의록이 이깁니다 — 단, 이기는 걸 확인하는 비용을 없애려면 어긋남 자체를 금지해야죠."

> **결의 1:** 전 심도 조준 가능, 자동 부상 제거. **카메라 규격 7항 확정** — ① `torpedoTubeAnchor` 단일 앵커, 카메라·어뢰 생성 동일 좌표계(개별 오프셋 계산 금지) ② 카메라 = 앵커 정위치 ③ 조준 중 자기 선체 렌더 제외 + 2D 발사관 튜브 프레임 UI(클리핑 원천 차단) ④ 어뢰 초기 방향 = 카메라 시선(십자선 = 탄도) ⑤ 조준 중 기동 허용(A/D 선체 선회 + 마우스 미세 조준각 콘) ⑥ 발사 후 조준경 유지, 해제는 우클릭 ⑦ '잠망경 심도 전용' 규칙을 전 문서에서 삭제, **코드-문서 동시 갱신 원칙** 신설. 마스크·비네트·FOV·덕킹 = 불가침 요소, 명칭 '어뢰 조준경', 관측 잠망경 백로그 보존.

## 안건 2. 어뢰 캠 — 채택 여부, 복귀 조건, 키 배정

**한도윤:** "관찰 3의 해결안 — **어뢰 캠.** 발사 직후 카메라가 어뢰를 따라가 명중까지 보여주는 기능입니다. '어뢰는 조작 결과의 최종 출력물'(5차)의 완성형이에요."

**강민준:** *(강한 반대)* "타이밍 반대. 성장 UI도 임시 화면인 마당에 카메라 장난감부터입니까. 3차 대회의였으면 컷 테이블 1번감입니다."

**정하늘:** "공수로 판정하죠 — 대상 추적 카메라: 있습니다(추적 대상만 잠수함→어뢰). 전환 보간: 있습니다(조준경 코드 재사용). 신규는 입력 처리와 복귀 판정뿐, **합계 1일.**"

**박태현:** "공수가 싸도 두 가지가 비어 있습니다. 첫째, 시청 중 잠수함은 무방비인데 **'위험하면 복귀'의 '위험'이 정의가 안 됐어요.** 피격? 탐지 게이지? 폭뢰 접근? 공격 상태 전환? 지형 충돌 직전? 내구도 임계? — 후보만 여섯 개입니다. 둘째, **키가 없습니다.** WASD·Shift·Ctrl·E·Space·H·마우스 양 버튼이 전부 사용 중이라, 대충 고르면 키 충돌이 납니다."

**정하늘:** "첫째부터. 여섯 후보를 다 넣으면 복귀 조건 자체가 하나의 시스템이 됩니다. MVP는 **세 개로 자릅니다** —

1. **잠수함 실제 피격** (가장 명확한 위험, 판정 이미 존재)
2. **탐지 상태의 경계(alert) 전환** (DetectionSystem의 기존 상태 전이 이벤트 재사용 — 폭뢰·공격 전환·추적은 전부 alert 이후에 오므로 이 하나가 상류에서 다 잡습니다)
3. **추적 중인 어뢰의 종료** (명중·소멸·사거리 만료 — 위험이 아니라 시청 대상의 소멸)

지형 충돌 직전 감지나 내구도 임계는 신규 판정 코드가 필요해서 제외. alert가 상류 신호라는 게 핵심입니다 — 하류의 개별 위협을 열거하는 대신 수도꼭지 하나를 잠그는 거죠."

**오세진 부재 관련 — 정하늘:** "키 배정은 개발팀 확인 사항이지만 키맵 표는 제가 갖고 있으니 여기서 확정합니다. 후보 검토 —

| 후보 | 판정 |
|---|---|
| Space | 기각 — 카메라 리센터 사용 중 |
| Q | 기각 — 좌손 이동 클러스터와 인접, 오입력 위험 |
| R | 기각 — 향후 재장전 수동 트리거 예약 |
| **F 홀드** | **채택** — 좌손이 WASD에서 닿되 이동 키와 비인접, 미사용 |

**F 홀드** — 발사 후 F를 누르는 동안 어뢰 시점, 떼면 즉시 복귀. 그리고 소회의 결의 1의 관례대로 **화면 버튼도 같은 진입점을 호출**합니다 — 발사 직후 화면 우하단에 '어뢰 추적' 버튼이 어뢰 수명 동안만 표시."

**이준호:** "복귀 조건 2번(alert 전환)에 사운드를 붙입니다 — 강제 복귀 직전 0.3초, 어뢰 주행음이 뚝 끊기고 잠수함 쪽 소나 핑이 확 커지면서 시점이 돌아옵니다. '왜 돌아왔는지'를 몸이 먼저 알게. 그리고 어뢰 캠 중에도 잠수함 위치 기준 위협 사운드는 상시 유지 — 카메라는 떠나도 귀는 잠수함에 남습니다."

**강민준:** "복귀 조건·키·버튼까지 규격이 닫혔으면 '장난감'이 아니라 '사양'이네요. 조건부 철회 — **어뢰 캠은 스프린트 A~C가 전부 끝난 뒤 잔여 시간에만 착수.** 보스 진입을 막는 조건에서도 제외합니다(안건 5)."

> **결의 2:** 어뢰 캠 채택 — **키 = F 홀드**(+ 어뢰 수명 동안만 노출되는 화면 버튼, 동일 진입점), 시간 정지 없음, 잠수함 기준 위협 사운드 상시 유지. **복귀 조건 3종 확정: ① 잠수함 피격 ② 탐지 alert 전환 ③ 어뢰 명중·소멸·사거리 종료** (지형 근접·내구도 임계 등은 제외 — alert가 상류에서 포괄). 착수 시점 = **스프린트 A~C 완료 후 잔여 시간**, 보스 진입 게이트에서 제외. 명중 슬로모션은 백로그.

## 안건 3. 스프린트 분할 — 우선순위가 아니라 종료 조건으로

**서지우:** "초안대로면 이번 스프린트에 조준 구조 변경, 어뢰 캠, UI 5종, params 이관, 중립·경비함·호위 수송선, 탐지·추적·폭뢰·침수·실패 화면까지 **열다섯 덩어리**가 들어갑니다. 우선순위 1·2·3은 정했지만, 하늘 님이 이 구성에 이의를 제기했습니다."

**정하늘:** *(강한 반대)* "우선순위만 있고 **종료 조건이 없는 계획**에 반대합니다. 순위표는 '무엇이 중요한가'만 말하지 '1순위가 언제 끝났는가'를 말하지 않아요. 이대로 개발에 넘기면 반드시 일어나는 일 — 1순위가 90%인 채로 2순위를 조금, 3순위를 조금 건드리는 **전선 확대**입니다. 열다섯 덩어리가 전부 80%인 빌드는 아무것도 완성 안 된 빌드예요. 제안: 한 스프린트가 아니라 **하위 스프린트 A/B/C 세 개**로 자르고, 각각에 검증 가능한 종료 조건을 붙입니다. **앞 스프린트의 종료 조건을 전부 통과하기 전에 다음 스프린트 착수 금지** — 순차 게이트 방식, 우리 게이트 리뷰의 4문 순차제와 같은 원리입니다."

**박태현:** "그 구조에는 찬성인데, 초안에서 제가 제기한 순서 반대를 여기서 다시 겁니다 — 생존 전투(C)가 검증된 코어인데 왜 맨 뒤입니까?"

**정하늘:** "초안에서의 답 그대로입니다 — C가 뒤인 이유는 덜 중요해서가 아니라 **덜 위험해서.** C는 전부 이월 자산(DetectionSystem·추적·폭뢰·X-ray)의 재배선이고, A는 존재한 적 없는 신규(구매 UI·경제 피드백)입니다. 미검증을 앞에, 검증을 뒤에."

**최윤아:** "그리고 데이터 의존성 — 호위함이 무서운지는 그 수송선이 탐나는지에 달렸고, 탐나는지는 크레딧으로 뭘 살 수 있는지에 달렸습니다. A 없이는 B·C의 튜닝 기준이 없어요."

**박태현:** "두 논거 재확인으로 철회 유지합니다. 그럼 종료 조건을 채웁시다."

**스프린트 A — 조준 수정과 성장 UI** *(종료 조건, 전 항목 통과 필수)*

| # | 종료 조건 |
|---|---|
| A1 | 전 심도에서 조준 진입 가능 |
| A2 | 조준 전후 잠수함 Y 위치 변화 없음 (자동 부상 제거 검증) |
| A3 | 십자선 중심과 어뢰 초기 진행 방향 일치 (앵커 좌표계 검증) |
| A4 | 크레딧·희귀 부품이 기지·해역 양쪽 UI에 표시 |
| A5 | 업그레이드 구매 성공·실패가 모두 동작하고 실패 시 사유 표시 |
| A6 | 장비 장착·교체·해제 동작 |
| A7 | 저장 후 재접속 시 구매·장착 상태 유지 |

**스프린트 C — 생존 전투** *(종료 조건)*

> **결의 3:** 단일 스프린트 기각 — **하위 스프린트 A(조준+성장 UI) → B(위험과 보상) → C(생존 전투) 순차 게이트 방식** 채택. 각 스프린트는 명시된 종료 조건 전 항목 통과로만 완료 판정, **미완료 상태에서 다음 스프린트 착수 금지.** 어뢰 캠은 A~C 밖(잔여 시간 항목). B7 오인율 판단 기준 튜닝표 등재(20% 초과 강화 / 5% 미만+시시함 응답 시 완화).

## 안건 4. 경제 데이터 선행 원칙 — "UI는 데이터의 그릇이지 데이터가 아니다"

**정하늘:** "스프린트 A 내부의 작업 순서 문제입니다. A5(구매 UI)를 먼저 만들고 가격을 나중에 채우면, 가격 자릿수·단계 표시·불가 사유가 확정될 때마다 UI를 다시 뜯습니다. 순서를 강제합니다 —

1. 업그레이드 7항목의 **공식 ID 확정**
2. 항목별 **단계 상한** 확정
3. 단계별 **가격** 확정
4. 단계별 **효과 배율** 확정
5. 장비 4종의 **가격·희귀 부품 요구량** 확정
6. **그 데이터에 맞춰** UI 구현

1~5가 태현 님 산출물이고, 이게 스프린트 A의 병목입니다. D+3 절대 마감의 재림이에요."

**박태현:** "받습니다. 그리고 6번 UI가 표시할 **구매 불가 사유**도 지금 닫죠. 후보 여섯 — 크레딧 부족 / 희귀 부품 부족 / 최대 단계 도달 / 선행 업그레이드 미충족 / 슬롯 부족 / 이미 장착 중. 이 중 '선행 업그레이드'는 논의가 필요합니다. 테크 트리를 넣을 겁니까?"

**강민준:** "신 스코프 가드를 소환합니다 — 업그레이드 7항목 캡은 트리가 아니라 평면 목록을 전제한 숫자예요. 선행 조건을 넣는 순간 트리 설계·해금 연출·밸런스가 줄줄이 딸려 옵니다. MVP 기각."

**박태현:** "동의합니다. 그러면 원칙 하나 — **구현하지 않는 기능의 사유 문구는 UI에서도 뺍니다.** '선행 업그레이드 미충족'이라는 문구가 코드에 존재하는 순간, 그건 개발팀 소회의가 금지한 '나중을 위한 스텁'입니다. 불가 사유는 5종으로 확정: 크레딧 부족 / 희귀 부품 부족 / 최대 단계 / 슬롯 부족 / 이미 장착 중."

**서지우:** "가격 데이터의 검증 도구는 이미 있습니다 — 임찬영 님의 업그레이드 시뮬레이터. 태현 님이 1~5를 params로 커밋하면 시뮬레이터에서 총비용 곡선을 미리 보고, '보스까지 몇 번의 출항이 필요한가'를 빌드 없이 계산할 수 있어요. 목표 수치도 정합시다 — 6차의 '첫 클리어 30~60분'을 역산하면 **보스 도전 최소 사양까지 출항 4~6회**가 적정선입니다. 이 범위를 벗어나면 가격 재조정."

> **결의 4:** 스프린트 A 내부 순서 강제 — **경제 데이터(ID·단계 상한·가격·배율·장비 비용) 확정 → UI 구현.** 데이터 확정은 박태현, 스프린트 A의 병목으로 지정. 선행 업그레이드(테크 트리) MVP 기각 — 신 스코프 가드 위반. **구매 불가 사유 5종 확정**(크레딧 부족/부품 부족/최대 단계/슬롯 부족/이미 장착 중), 미구현 기능의 사유 문구는 UI·코드 모두 금지(스텁 금지 원칙 준용). 가격 검증 기준: 보스 도전까지 출항 4~6회(시뮬레이터로 사전 검증, 이탈 시 재조정).

## 안건 5. 보스 진입 게이트 — 전체 완료가 아니라 핵심 완료

**서지우:** "초안에서 우리는 '이 스프린트 전체 완료 = 보스 투입 조건'이라고 적었습니다. 하늘 님이 이 조건에 이의를 냈습니다."

**정하늘:** "포괄 조건의 문제는 **사소한 것이 핵심을 인질로 잡는다**는 겁니다. 구매 UI의 마감 디테일 하나, 어선 뱃고동 하나가 안 끝났다고 보스 작업 전체가 대기하는 상황 — 그건 게이트가 아니라 정체예요. 보스 진입 게이트는 '보스전이 성립하기 위한 필요조건'만으로 좁혀야 합니다. 제안 6조 —

1. 전 심도 조준 + 자동 부상 제거 완료 (A1~A3)
2. 구매·장착·저장 루프 완료 (A4~A7)
3. 적대·중립 식별 + 경비함 스폰 완료 (B1~B5)
4. 탐지·피격·내구도·파괴 완료 (C1~C6)
5. 귀환·실패 정산 분리 완료 (C7~C8)
6. 임시 전투·경제 수치의 params 이관 완료 (A8)

**게이트 제외 항목** — 어뢰 캠, 중립 선박 고유 사운드, 실패 화면 고급 연출, B6 보상 배율의 최종 튜닝, B7 오인율 측정. 이것들은 스프린트 종료 조건에는 남지만, 보스 '시작'을 막지는 않습니다."

**김세라:** *(경계 발언)* "잠깐 — '연출은 게이트 제외'가 관성이 되는 건 경계합니다. 2차 회의 보호 목록(60fps·폭뢰 동기화·X-ray 침수·파문)이 컷 테이블 상위 문서였던 걸 기억하시죠. 지금 제외 목록에 X-ray가 없는 건 확인했습니다만, 기록으로 남겨주세요 — **게이트 제외는 '보스 시작을 막지 않는다'는 뜻이지 '안 만들어도 된다'는 뜻이 아니다.** 스프린트 종료 조건에는 그대로 살아 있고, 보호 목록은 여전히 상위 문서입니다."

**정하늘:** "정확한 구분이고 전적으로 동의합니다. C5의 X-ray 침수는 게이트 4항 '내구도·파괴'에 포함돼 있어요 — 보호 목록 항목은 게이트 안에 있습니다. 제외된 건 보호 목록 밖의 부가 연출뿐입니다."

**강민준:** "그럼 두 단어를 구분해서 씁시다 — 스프린트 **종료 조건**(전 항목, 스프린트의 완료 정의)과 보스 **진입 게이트**(6조, 보스 착수의 허가 조건). 종료 조건 미달 항목은 보스 작업과 병렬로 마저 끝냅니다. 채택."

> **결의 5:** 보스 진입 게이트 = **핵심 6조**(조준 수정 / 구매·장착·저장 루프 / 식별·경비함 / 탐지·피격·파괴 / 정산 분리 / params 이관)로 확정. 어뢰 캠·고유 사운드·고급 연출·최종 튜닝·오인율 측정은 게이트에서 제외하되 **스프린트 종료 조건에는 존치**(병렬 마감). '게이트 제외 ≠ 제작 면제' 명문화, 보호 목록(X-ray 침수 포함)은 게이트 내 존재 확인.

## 최종 결의안

1. 조준은 전 심도에서 가능하며 조준 전후 잠수함의 심도는 변하지 않는다.
2. 선수 조준 카메라는 **규격 7항**(단일 앵커 `torpedoTubeAnchor`·동일 좌표계·정위치 카메라·자기 선체 렌더 제외 + 2D 튜브 프레임·시선 = 탄도·조준 중 기동 허용·발사 후 유지·문서 동시 갱신)을 따른다.
3. '잠망경 심도 전용' 규칙을 모든 상태 문서·체크리스트에서 삭제하고, **코드-문서 동시 갱신 원칙**을 신설한다.
4. 어뢰 캠은 **F 홀드 + 화면 버튼**(동일 진입점)으로 채택하되, 복귀 조건은 **피격 / 탐지 alert 전환 / 어뢰 종료** 3종으로 한정하고, 착수는 스프린트 A~C 완료 후 잔여 시간으로 한다.
5. 스프린트는 **A(조준+성장 UI) → B(위험과 보상) → C(생존 전투)**의 순차 게이트로 분할하고, 각 스프린트는 명시된 종료 조건 전 항목 통과로만 완료된다. 미완료 상태의 다음 스프린트 착수를 금지한다.
6. 스프린트 A는 **경제 데이터 확정(ID·단계·가격·배율·장비 비용) → UI 구현** 순서를 강제한다. 데이터 확정이 병목이며 담당은 게임 디자이너다.
7. 테크 트리(선행 업그레이드)는 MVP에서 기각하고, 구매 불가 사유는 5종으로 확정하며, 미구현 기능의 문구·스텁을 금지한다.
8. 가격 밸런스 기준은 '보스 도전까지 출항 4~6회'로 하고 시뮬레이터로 사전 검증한다.
9. 보스 진입 게이트는 핵심 6조로 한정한다. 게이트 제외 항목은 스프린트 종료 조건에 존치하며 보스 작업과 병렬로 완료한다.
10. 적대·중립 오인 사격률의 판단 기준(20% 초과 시각 강화 / 5% 미만+시시함 시 완화)을 튜닝표에 등재한다.
