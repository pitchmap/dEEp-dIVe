## 안건 1. 순차 게이트 × 보스 게이트 — "제외했는데 제외되지 않았다"

**임찬영:** "발견 경위부터. 스프린트 일정표를 짜다가 막혔습니다. 7차 결의에 이 네 문장이 동시에 존재합니다 —

1. B가 **전부** 끝나야 C 착수 (결의 3, 순차 게이트)
2. B6(보상 튜닝)·B7(오인율 측정)은 B의 종료 조건 (결의 3)
3. B6·B7은 보스 진입 게이트에서 **제외** (결의 5)
4. B6·B7은 보스 작업과 **병렬 마감** 가능 (결의 5)

그런데 보스 진입에는 C1~C8이 필요하고, C는 B가 전부 끝나야 시작합니다. 즉 B6·B7이 안 끝나면 → C를 못 시작하고 → C가 없으면 보스도 못 시작합니다. **결의 5의 '게이트 제외'가 결의 3에 의해 무효화**돼 있어요. 병렬 마감하라는 항목이 실제로는 모든 것을 직렬로 막고 있습니다."

**정하늘:** "…정확한 지적이고, 제가 결의 5를 제안하면서 결의 3과의 교차 검증을 안 한 겁니다. 해결안은 두 갈래인데 —"

**오세진:** *(이견 1건)* "간단한 쪽부터 제안합니다. B6·B7을 그냥 B에서 **빼버리죠.** '기타 마감' 목록으로 옮기면 충돌이 사라집니다."

**정하늘:** *(반대)* "그 단순함이 함정입니다. 종료 조건에서 빠진 항목의 운명을 우리는 압니다 — **영원히 안 끝납니다.** '기타 목록'은 백로그의 다른 이름이에요. B7 오인율 측정은 서지우 님이 튜닝표 판단 기준까지 걸어둔 항목인데, 소속 없는 목록으로 보내면 측정 자체가 증발합니다. 대안 — 각 스프린트를 **두 단계로 분리**합니다.

- **핵심 게이트**: 통과 시 다음 스프린트 착수 허가
- **최종 종료 조건**: 다음 스프린트와 병렬 마감 가능, 단 스프린트 '완료' 선언에는 필수

B에 적용하면 —

| 구분 | 항목 | 효과 |
|---|---|---|
| **B 핵심 게이트** | B1 동시 배치 / B2 식별 태그 / B3 중립 보상 미지급 / B4 경비함 스폰 / B5 구축함 AI 재사용 | 통과 즉시 C 착수 가능 |
| **B 최종 종료** | B6 보상 튜닝 / B7 오인율 측정 | C·보스와 병렬, 완료 선언의 필수 조건 |

같은 원리로 C도 — **C 핵심 게이트 = C1~C6**(탐지·추적·폭뢰·내구도·파괴·실패 화면), **C 최종 종료 = C7~C8**(정산 분리·영구 요소 유지 검증)… 아니, 잠깐. C7·C8은 보스 진입 게이트 6조의 5항(정산 분리)에 들어 있으니 핵심에 남아야 합니다. C는 분리 실익이 없네요 — **C1~C8 전부 핵심 게이트**, 분리는 A·B만. A는 A1~A8 전부가 보스 게이트 1·2·6항에 걸려 있으니 역시 전부 핵심."

**임찬영:** "그럼 최종 구조 — A 전부 핵심 / B만 핵심(B1~B5)·최종(B6~B7) 분리 / C 전부 핵심. 항목이 게이트에 걸려 있느냐로 기계적으로 판정되니 일정표가 짜집니다. 이거면 됩니다."

**오세진:** "'기타 목록' 안 철회합니다. 두 단계 구조가 측정 항목을 지키네요."

> **결의 1:** 스프린트를 **핵심 게이트 / 최종 종료 조건** 2단계로 분리. **A = 전 항목 핵심 / B = 핵심 B1~B5(통과 시 C 착수) + 최종 B6~B7(C·보스와 병렬, 완료 선언 필수) / C = 전 항목 핵심.** 판정 기준: 보스 진입 게이트 6조에 걸린 항목은 핵심, 아니면 최종. 7차 결의 3·5의 충돌은 본 결의로 해소(각주 개정).

## 안건 2. 앵커 규격 보완 — "정확히 같은 위치는 정확히 같은 사고를 부른다"

**남유리:** "결의 1-①·②를 코드로 옮기다 발견했습니다. '카메라 = 앵커 정위치, 어뢰 생성 = 동일 앵커'를 문자 그대로 구현하면 — **발사 순간 어뢰가 카메라 위치에서 생성됩니다.** 근접 평면(near plane)이 어뢰 모델을 반쯤 자르면서 화면 전체가 어뢰 내부 폴리곤으로 번쩍이고, 최악의 경우 한 프레임 동안 카메라가 어뢰 '안'에 있어요. 대회의가 금지한 '개별 오프셋 계산'의 취지는 맞는데, 오프셋 **제로**는 다른 종류의 사고입니다."

**정하늘:** "취지는 살리고 규격만 고치죠. 제안 —

```text
torpedoTubeAnchor          (모델 정의, 단일 진실 공급원)
 ├─ aimCameraSocket        (앵커 정위치·동일 전방축)
 └─ torpedoSpawnSocket     (동일 전방축 + 고정 전방 안전 오프셋)
```

두 소켓은 같은 앵커·같은 전방축을 공유하고, 안전 오프셋은 **소켓 정의 한 곳에만** 존재합니다. 카메라 시스템도 어뢰 시스템도 자기 오프셋을 계산하지 않고 소켓을 읽기만 해요. 대회의 금지 조항의 정신 — '각자 계산 금지' — 은 그대로, 물리적 사고만 제거됩니다. 결의 문구도 바꿉니다: '카메라와 어뢰 생성 위치는 torpedoTubeAnchor의 동일 좌표계와 전방축을 공유한다. 단, 근접 클리핑과 자기 충돌 방지를 위한 고정 안전 오프셋은 공통 소켓 정의에서만 허용하며 시스템별 개별 계산은 금지한다.'"

**남유리:** "채택하고 하나 더 — 결의 1-③ '조준 중 자기 선체 렌더 제외'도 위험한 문장입니다. 이걸 객체 숨김(visible = false)으로 구현하면 **잠수함이 세계에서 사라집니다** — 그림자가 없어지고, 수면 파문이 끊기고, 향후 리플레이·관전 카메라에서도 배가 없어요. 올바른 구현은 **조준 카메라의 레이어 마스크에서만 자기 선체 메시를 제외**하는 겁니다. 세계는 잠수함을 계속 알고, 조준 카메라만 모르는 척하는 거죠. 문구 명시를 요청합니다."

**정하늘:** "구현 방식이 결의 취지를 배반할 수 있는 전형적 사례네요. 명시합니다."

> **결의 2:** 앵커 규격 개정 — **aimCameraSocket / torpedoSpawnSocket 2소켓 구조**, 동일 앵커·동일 전방축, 안전 오프셋은 소켓 정의 단일 지점에만 허용(시스템별 계산 금지 유지). 자기 선체 렌더 제외는 **조준 카메라의 레이어 마스크 방식으로 한정** — 객체 전역 숨김 금지(그림자·파문·타 카메라 보존).

## 안건 3. 미세 조준각 — 콘의 크기가 없으면 콘이 아니다

**오세진:** "결의 1-⑤ '마우스 미세 조준각(제한된 콘 범위)' — 구현하려니 콘의 각도, 감도, 그리고 해제 후 거동이 전부 없습니다. 3차 결의 2 원칙대로 하드코딩은 못 하니, params 항목부터 정의해야 합니다."

**정하늘:** "다섯 항목으로 자릅니다. 초기값은 전부 '초기 테스트값' 지위 —

| 파라미터 | 초기값 | 조정 범위 | 비고 |
|---|---|---|---|
| `aimYawLimitDegrees` | ±15° | 10~25° | 좌우 미세각. 큰 각은 A/D 선체 선회 |
| `aimPitchUpLimitDegrees` | +10° | 5~15° | 상향은 좁게 — 수면 배는 조준경 상단에 걸림 |
| `aimPitchDownLimitDegrees` | −15° | 10~25° | 하향은 넓게 — 해저 보물·수중 적 대응 |
| `aimMouseSensitivity` | 0.5 (일반 카메라 대비) | 0.3~1.0 | 조준 중 감도 하향 = 정밀 조준감 |
| `aimReturnBehavior` | reset | reset / persist | 아래 결정 |

`aimReturnBehavior`가 오늘 결정할 항목입니다. 조준 해제 후 미세각을 **유지(persist)**하느냐 **초기화(reset)**하느냐."

**오세진:** "**reset**을 주장합니다. persist의 문제 — 아까 아래로 15° 꺾어둔 걸 잊고 다음 조준에 들어가면, 카메라가 예상 밖 방향을 보면서 '조준경이 고장났나' 하는 0.5초가 생깁니다. 조준 진입은 항상 선수 정면에서 시작하는 게 예측 가능성 원칙에 맞아요. 그리고 좌표 기준도 함께 — 미세각은 **잠수함 로컬 좌표 기준**으로 유지합니다. 조준 중 A/D로 선체가 돌면 조준선도 선체와 함께 돌고, 미세각은 그 위에 얹히는 상대각. 월드 기준으로 하면 선회 중에 조준선이 세계에 고정돼서 배와 따로 놉니다."

**남유리:** "reset에 한 표 더 — persist면 '현재 미세각이 얼마나 꺾여 있는지' UI 표시가 추가로 필요해집니다. reset은 그 UI 자체가 불필요."

**정하늘:** "reset + 로컬 기준, 채택. 다섯 파라미터는 `/params/aiming.json` 신설, 태현 님 커밋 권한 범위에 추가."

> **결의 3:** 미세 조준각 params 5종 신설(`aiming.json`) — yaw ±15°, pitch +10°/−15°, 감도 0.5, 전부 초기 테스트값·튜닝표 등재. **`aimReturnBehavior` = reset**(해제 시 초기화), 미세각은 **잠수함 로컬 좌표 기준**(선체 선회 시 함께 회전). persist는 params 값으로 남겨 플레이테스트 비교 가능하게 유지.

## 안건 4. 기지 저장 시점 — A7의 함정

**임찬영:** "A7 종료 조건 — '저장 후 재접속 시 구매·장착 상태 유지' — 를 검증 시나리오로 쓰다가 구멍을 발견했습니다. 현행 저장 시점은 개발 소회의 결의 3에서 딱 두 개예요: **귀환 정산 확정 / 희귀 부품 획득 즉시.** 그런데 기지에서 업그레이드를 사고 **출항하지 않은 채 새로고침하면?** 저장 시점이 안 왔으니 구매가 증발합니다. 크레딧은 차감됐는데 업그레이드는 없는, 최악의 데이터 유실이에요. A7은 지금 규격으로는 **통과 불가능한 종료 조건**입니다."

**오세진:** "선택지는 둘 — 상태 변경마다 dirty 플래그를 세우고 기지 화면 종료·출항 시점에 몰아서 저장하거나, 변경 즉시 저장하거나."

**임찬영:** "**즉시 저장**을 주장합니다. dirty 방식의 문제 — '기지 화면 종료'는 새로고침·탭 닫기를 포착 못 합니다. beforeunload 이벤트는 브라우저마다 신뢰도가 달라서, 정확히 A7이 검증하려는 그 시나리오(새로고침)에서 구멍이 나요. 즉시 저장은 로컬 저장 쓰기라 비용이 밀리초 단위고, 기지에서는 초당 수십 번 구매할 일도 없습니다. 단순한 쪽이 검증 가능한 쪽입니다."

**정하늘:** "채택. 저장 시점을 공식 개정합니다 — 기존 2종에 3종 추가:

1. 귀환 정산 확정 (기존)
2. 희귀 부품 획득 즉시 (기존)
3. **업그레이드 구매 성공 직후** (신설)
4. **장비 장착·교체·해제 직후** (신설)
5. **출항 확정 직전** (신설 — 출항 시점의 최종 상태 봉인)

해역 내 자동 저장 없음은 유지 — '귀환이냐 한 탕이냐'의 긴장은 6차 결의 7의 심장이니까."

> **결의 4:** 저장 시점 5종으로 개정 — 기존(귀환 정산·희귀 부품) + **구매 성공 직후·장착 변경 직후·출항 확정 직전.** dirty 플래그 방식 기각(새로고침 미포착 — A7 검증 불가). 해역 내 자동 저장 없음 유지. 개발 소회의 결의 3에 각주 개정.

## 안건 5. params 이관 범위 — A8과 보스 게이트의 문서 불일치

**임찬영:** "문서 대조에서 나온 불일치입니다. A8은 '**임시 경제 수치** 전량 이관', 보스 게이트 6항은 '임시 **전투·경제** 수치 전량 이관'. 전투 임시값 — 탐지 속도, 폭뢰 피해, 내구도, 침수율 — 의 이관이 어느 스프린트 종료 조건에도 소속돼 있지 않아요. 게이트는 요구하는데 아무도 담당하지 않는 항목입니다."

**정하늘:** "소속을 만들어 주면 됩니다. 전투 임시값이 확정되는 시점은 생존 전투가 배선되는 C니까 — **C9 신설: '탐지·폭뢰·내구도·침수 관련 임시값 전량 공식 params 이관.'** C 핵심 게이트에 포함(보스 게이트가 요구하니까). 보스 게이트 6항은 'A8 + C9 완료 확인'으로 문구 수정. 커밋 태그도 분리합니다 — 경제는 기존 [ECON], 전투 수치는 **[COMBAT] 신설.** 게이트 리뷰에서 '언제 폭뢰 피해가 바뀌어 난이도가 무너졌나'를 경제 커밋과 섞이지 않게 역추적하려면 태그가 갈라져 있어야 해요."

**서지우 (배석 발언):** "기획 접점 — [COMBAT] 태그 의무를 태현 님의 `/params` 직접 커밋 규칙에도 전파하겠습니다. 튜닝표의 담당 열과 태그가 일치하도록."

> **결의 5:** **C9 신설**(전투 임시값 — 탐지·폭뢰·내구도·침수 — 전량 params 이관, C 핵심 게이트 소속). 보스 게이트 6항 문구를 'A8+C9 완료'로 개정. 커밋 태그 **[COMBAT] 신설**, [ECON]과 분리 운용.

## 안건 8. 하향 제한각의 부호 규칙  
### “설정값은 크기이고, 방향은 계산이 결정한다”

**오세진:**  
“기존 결의 3의 파라미터 표에 부호가 섞여 있습니다.

```text
aimPitchDownLimitDegrees
초기값: -15
조정 범위: 10~25
```

초기값은 음수인데 validator 범위는 양수입니다. 구현자가 값 자체를 음수로 볼지, 하향 각도의 크기로 볼지 달라질 수 있습니다.

JSON 스키마에서는 방향이 아니라 허용 각도의 크기만 저장하는 편이 안전합니다.”

**정하늘:**  
“상향·하향 제한값은 모두 0 이상의 절댓값으로 저장하고, 실제 회전 계산에서만 부호를 적용하겠습니다.

```json
{
  "aimPitchUpLimitDegrees": 10,
  "aimPitchDownLimitDegrees": 15
}
```

런타임 허용 범위는 다음과 같습니다.

```text
최소 피치 = -aimPitchDownLimitDegrees
최대 피치 = +aimPitchUpLimitDegrees
```

JSON에 음수 방향 정보를 넣지 않습니다.”

**임찬영:**  
“validator도 양수만 받도록 맞추겠습니다.

- `aimPitchUpLimitDegrees`: 5~15
- `aimPitchDownLimitDegrees`: 10~25

0 이하 값, 음수 값, 범위 밖 값은 로드 거부 대상으로 처리합니다.”

**남유리:**  
“그래픽스와 카메라 코드도 동일한 계산 함수를 사용해야 합니다. 카메라에서 한 번 음수를 붙이고 게임플레이에서 또 음수를 붙이는 이중 부호 오류를 막아야 합니다.”

> **결의 8:**  
> `aimPitchUpLimitDegrees`와 `aimPitchDownLimitDegrees`는 모두 **양의 각도 크기**로 저장한다.
>
> ```text
> aimPitchUpLimitDegrees = 10
> aimPitchDownLimitDegrees = 15
> ```
>
> 실제 피치 제한 계산 시에만 하향 방향에 음수를 적용한다.
>
> ```text
> pitchMin = -aimPitchDownLimitDegrees
> pitchMax = +aimPitchUpLimitDegrees
> ```
>
> - JSON 원본에 음수 하향각을 저장하지 않는다.
> - validator 범위도 양수 기준으로 통일한다.
> - 카메라·조준·테스트 코드가 동일한 제한 계산 함수를 사용한다.
> - 기존 문서의 `−15°` 표기는 `15° 하향`으로 수정한다.

### 개정된 `/params/aiming.json` 초기값

```json
{
  "aimYawLimitDegrees": 15,
  "aimPitchUpLimitDegrees": 10,
  "aimPitchDownLimitDegrees": 15,
  "aimMouseSensitivity": 0.5
}
```

## 안건 9. `aimReturnBehavior`의 지원 범위  
### “구현하지 않을 선택지는 스키마에도 넣지 않는다”

**남유리:**  
“기존 결의에서는 조준 해제 시 `reset`을 사용하기로 확정하면서, 플레이테스트 비교를 위해 `persist`도 params 선택지로 남기기로 했습니다.

그런데 스프린트 A에서 실제로 `persist`를 구현하지 않는다면 JSON 스키마만 두 값을 허용하는 상황이 됩니다. 사용 가능한 것처럼 보이지만 실제로는 동작하지 않는 선택지입니다.”

**오세진:**  
“그건 우리가 경제 UI에서 금지한 ‘미구현 기능의 스텁’과 같습니다. `persist` 값을 넣었는데 코드가 무시하거나 `reset`처럼 동작하면 설정 파일이 거짓말을 하게 됩니다.”

**정하늘:**  
“스프린트 A에서는 비교 실험보다 안정된 기본 동작을 먼저 완성합니다.

결정을 다음처럼 수정합니다.

- 스프린트 A에서는 `reset`만 지원
- `aimReturnBehavior`를 사용자 조정용 params 항목으로 노출하지 않음
- 조준 해제 시 미세 조준각은 항상 0으로 초기화
- `persist` 비교가 실제 플레이테스트 안건으로 승인되는 시점에만 구현과 스키마를 함께 확장

즉, 지금은 동작 하나만 있으므로 설정값 자체가 필요 없습니다.”

**임찬영:**  
“향후 `persist`를 추가할 경우 다음이 한 작업 단위에 포함되어야 합니다.

1. 스키마 enum 확장
2. 게임플레이 구현
3. 카메라 구현
4. 테스트
5. 상태 문서 갱신
6. 기존 저장 데이터와 관련 있으면 마이그레이션 검토

설정값만 먼저 추가하는 커밋은 리뷰에서 반려하겠습니다.”

> **결의 9:**  
> 스프린트 A에서는 **`reset` 동작만 지원**한다.
>
> - 조준 해제 시 yaw·pitch 미세 조준각을 0으로 초기화한다.
> - `aimReturnBehavior`를 `/params/aiming.json`에 포함하지 않는다.
> - `persist` 값이나 분기 스텁을 코드·스키마에 미리 만들지 않는다.
> - `persist` 비교 테스트가 정식 승인될 경우 구현·스키마·테스트·문서를 동시에 추가한다.
>
> 기존 결의의 “persist를 params 값으로 남긴다”는 문구는 본 결의로 폐기한다.

### 스프린트 A의 조준 해제 규칙

```text
조준 해제
→ 카메라 조준 오프셋 초기화
→ yaw = 0
→ pitch = 0
→ 다음 조준 진입은 선수 정면에서 시작
```

## 안건 10. B7 적대·중립 오인 사격률 측정 규격  
### “측정값에는 분모와 최소 표본이 필요하다”

**서지우:**  
“기존 B7은 오인 사격률을 측정하고, 20% 초과면 시각 구분을 강화하며, 5% 미만이면서 구분이 시시하다는 반응이 있으면 완화하기로 했습니다.

하지만 오인 사격률의 계산식과 최소 표본이 없으면 같은 테스트 결과를 두고도 서로 다른 숫자를 만들 수 있습니다.”

**정하늘:**  
“측정 단위를 먼저 정의해야 합니다. 단순히 발사된 어뢰 전체를 분모로 쓰면 적대 선박 전투 숙련도가 섞입니다.

B7의 목적은 ‘플레이어가 적대와 중립을 구분할 수 있는가’이므로, 분모는 **식별 후 공격 여부를 결정한 기회**가 되어야 합니다.”

**서지우:**  
“계산식을 다음으로 확정하겠습니다.

```text
오인 사격률 =
중립 선박을 적대 선박으로 오인하여 공격한 횟수
÷
적대·중립 선박을 식별한 뒤 공격 여부를 결정한 전체 횟수
× 100
```

중립 선박을 고의로 공격한 경우는 오인이 아니므로 별도 기록합니다. 테스터 인터뷰에서 ‘중립인 것을 알고도 공격했다’고 확인되면 오인 사격 분자에서 제외하되, 중립 공격 행동 기록에는 남깁니다.”

**오세진:**  
“조작 실수도 분리해야 합니다. 조준경 태그를 중립으로 정확히 읽었지만 좌클릭을 잘못 눌렀다고 명확히 확인된 경우, 식별 오류가 아니라 입력 오류입니다.”

**서지우:**  
“동의합니다. 다만 테스터의 사후 진술만으로 무조건 제외하면 결과가 왜곡될 수 있으니, 화면 녹화·입력 로그·직후 인터뷰 중 두 개 이상이 일치할 때만 조작 실수로 분류합니다.”

**임찬영:**  
“최소 표본은 다음을 적용하겠습니다.

- 테스터 최소 5명
- 전체 유효 식별 기회 최소 50회

두 조건 중 하나라도 충족하지 못하면 비율을 계산하더라도 합격·실패 판정에는 사용하지 않고 ‘표본 부족’으로 기록합니다.”

**남유리:**  
“시각 강화 판단이 필요한 경우 무엇을 바꾸는지도 미리 우선순위를 두면 좋겠습니다.”

**서지우:**  
“오인율 20% 초과 시 강화 순서는 다음과 같이 하겠습니다.

1. 조준경 식별 태그 가독성
2. 항해등과 색 대비
3. 실루엣 차이
4. 사운드 구분

가장 저비용이면서 직접적인 태그부터 수정하고, 한 번에 모든 요소를 과장하지 않습니다.”

> **결의 10:**  
> B7의 적대·중립 오인 사격률은 다음 공식으로 측정한다.
>
> ```text
> 오인 사격률 =
> 중립 선박을 적대 선박으로 오인하여 공격한 횟수
> ÷
> 적대·중립 식별 후 공격 여부를 결정한 전체 유효 기회
> × 100
> ```
>
> 최소 표본:
>
> - 테스터 5명 이상
> - 전체 유효 식별 기회 50회 이상
>
> 두 조건을 모두 충족해야 공식 판정에 사용할 수 있다. 미충족 시 결과는 참고치로만 기록하고 판정은 보류한다.
>
> 다음은 오인 사격 분자에서 제외하고 별도 기록한다.
>
> - 중립임을 알고 의도적으로 공격한 경우
> - 식별은 정확했으나 조작 실수로 발사한 경우
> - 태그 표시 전 발사하여 식별 기회 자체가 없었던 경우
>
> 조작 실수 제외는 화면 기록·입력 로그·직후 인터뷰 중 2개 이상이 일치할 때만 인정한다.
>
> 기존 판단 기준은 유지한다.
>
> - 오인 사격률 20% 초과: 시각·식별 정보 강화
> - 오인 사격률 5% 미만이면서 “구분이 지나치게 단순하다”는 정성 응답이 반복될 경우: 식별 정보 완화 검토
> - 5~20%: 현 상태 유지 후 추가 관찰

# 개정 후 스프린트 A 관련 최종 규격

## 조준 파라미터

```json
{
  "aimYawLimitDegrees": 15,
  "aimPitchUpLimitDegrees": 10,
  "aimPitchDownLimitDegrees": 15,
  "aimMouseSensitivity": 0.5
}
```

- 미세 조준각은 잠수함 로컬 좌표 기준
- 조준 해제 시 yaw·pitch 모두 0으로 초기화
- `persist` 미지원
- 음수 제한각을 params에 저장하지 않음

## 구매 트랜잭션

```text
구매 전 상태 저장
→ 조건 검증
→ 크레딧 차감
→ 업그레이드 적용
→ 로컬 저장
→ 성공 확정

저장 실패
→ 크레딧 롤백
→ 업그레이드 롤백
→ 저장 실패 안내
```

## B7 공식 판정 조건

```text
테스터 ≥ 5명
전체 유효 식별 기회 ≥ 50회
```

표본 조건 미달 시 오인 사격률은 참고치로만 기록하며 적대·중립 시각 구분의 강화·완화 결정을 내리지 않는다.
