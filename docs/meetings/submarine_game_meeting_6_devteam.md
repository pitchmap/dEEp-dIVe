## 안건 1. 엔진·기술 스택 확정

**남유리:** "선택지는 셋입니다. Three.js / Babylon.js / Unity WebGL. 저는 **Unity WebGL**을 밀고 싶습니다. 물 셰이더, 물리, 애니메이션 전부 내장이고, 저희 셋 다 Unity 경험이 있어요. 15일 일정에서 엔진이 주는 기성품의 가치는 큽니다."

**임찬영:** *(강한 반대)* "빌드 담당으로서 반대합니다. 숫자로 말씀드릴게요. Unity WebGL 빈 프로젝트 빌드가 압축 후에도 수 MB대 중반에서 시작하고, 물리·오디오 모듈 얹으면 금방 20MB를 넘습니다. 우리 게이트는 **초기 다운로드 15MB, 접속 3초**예요. Unity로는 G2 게이트를 시작도 전에 접는 겁니다. 게다가 WebGL 빌드는 이터레이션이 느립니다 — 수정 한 번에 빌드 몇 분씩 기다리면 15일 안에 튜닝 사이클이 안 돌아요. Three.js는 저장하면 1초 만에 브라우저 리로드입니다."

**남유리:** "Three.js로 가면 물, 파티클, X-ray 렌더링 전부 손으로 짜야 합니다. 그 공수는요?"

**정하늘:** "그게 오늘 제 판단 근거입니다 — 우리 아트 방향이 이미 그 공수를 지워줬어요. 로우폴리 + 플랫 셰이딩 + 반사 없는 물 + 그림자는 블롭만. 2차 대회의 성능 예산표를 보면 우리가 Unity에서 쓸 기능이 거의 없습니다. 화려한 걸 못 만들어서 Three.js가 위험한 게 아니라, **화려한 걸 안 만들기로 이미 결정했기 때문에 Three.js로 충분한** 겁니다. 바이브세일이 실증 사례고요."

**남유리:** "…성능 예산표 기준이면 인정합니다. 철회하되 조건 하나 — X-ray 반투명 렌더링은 제가 첫 주에 기술 검증(스파이크)부터 하게 해주세요. Three.js에서 안 예쁘게 나오면 그때는 구현 방식(스텐실 vs 투명도 정렬)을 다시 논의합니다."

**정하늘:** "승인. 스택 확정합니다 — **Three.js + Vite + TypeScript**, 물리는 풀 엔진 없이 자체 간이 물리(구 충돌 + 밀려남 벡터), 오디오는 **Web Audio API**(카메라 기준 패너), 파라미터는 3차 결의대로 **JSON 외부 파일**, 배포는 정적 호스팅 + CDN."

> **결의 1:** Three.js + Vite + TS / 자체 간이 물리 / Web Audio API / JSON 파라미터 / 정적 배포. X-ray 렌더링은 1주차 기술 스파이크로 검증

## 안건 2. 개발 5단계 프로세스 확정

**정하늘:** "전달받은 5단계 계획을 개발 일정으로 번역합니다. 원칙은 하나 — **그래픽보다 조작이 먼저, 조작보다 계측이 먼저.**"

| 단계 | 내용 | 기간 | 완료 판정 (Exit Criteria) |
|---|---|---|---|
| **0. 환경 구축** | 엔진·저장소·브랜치·배포 파이프라인 + **FPS/로딩 계측 오버레이** | D1~D2 | 빈 씬이 URL로 배포되고 fps·로딩 시간이 화면에 찍힘 |
| **1. 회색 박스** | 캡슐 잠수함: 이동→선회→심도 3층→카메라 회전·리센터→회색 협곡 통과 | D3~D5 | 팀 전원이 브라우저에서 조작해보고 관성 1차 튜닝 완료. **D+5 빌드 = 이것** |
| **2. 코어 전투 루프** | 화물선 배치→탐지→수동 조준·리드샷→어뢰→격침→구축함 등장→폭뢰→회피→탈출 | D6~D9 | 처음부터 끝까지 죽지 않고 1회 클리어 가능한 '최초의 게임' |
| **3. 은신·탐지** | 소음(속도 연동)·파문·지형 엄폐·심도 보정·발사 지점 노출·침묵 항행·눈 아이콘 | D10~D12 | 발각을 '피해서' 클리어하는 플레이와 '들켜서 쫓기는' 플레이가 모두 성립. **D+10 빌드 = 2단계+3단계 일부** |
| **4. 연출 적용** | 로우폴리 모델 교체·폭뢰 사운드 동기화·X-ray 침수·최소 UI·엔진/소나음·포그·조명 | D13~D14 | 보호 목록 4종(60fps·폭뢰 동기화·X-ray 침수·파문) 전부 작동 |
| **5. 통합·게이트 준비** | 최적화·저사양 모드·테스트 빌드 봉인 | D15 | G1·G2 자체 측정 통과, **D+15 빌드 = 게이트 제출본** |

**오세진:** *(반대 1건)* "2단계와 3단계 순서에 이의 있습니다. 탐지 시스템 없이 코어 루프를 먼저 만들면, 2단계의 '탐지'는 가짜(거리만 재는 임시 코드)로 짜야 하고 3단계에서 그걸 뜯어냅니다. 이중 작업이에요. 3단계를 2단계에 합치죠."

**정하늘:** "이중 작업 맞습니다. 알고 하는 겁니다. 이유는 **리스크 순서** — 우리 최대 리스크는 탐지 밸런스가 아니라 'D9까지 게임이 안 돌아가는 것'입니다. 2단계 끝에 '어쨌든 처음부터 끝까지 도는 빌드'가 존재해야, 3단계가 밀려도 게이트 리뷰에 낼 물건은 있는 거예요. 임시 탐지 코드는 버리는 비용 반나절입니다. 반나절로 '빈손 리스크'를 사는 보험이라고 생각해주세요."

**오세진:** "…보험 논리면 수용합니다. 대신 임시 탐지도 처음부터 인터페이스(DetectionSystem)를 분리해서 짜게 해주세요. 뜯어낼 때 반나절이 아니라 한 시간이 되게."

**정하늘:** "그건 그냥 좋은 설계네요. 채택."

> **결의 2:** 6단계(0~5) 일정 확정, 주간 빌드 3회(D+5/+10/+15)와 정렬 / 2단계 임시 탐지 허용하되 인터페이스 분리 의무 / 각 단계는 Exit Criteria로만 완료 판정

## 안건 4. 브랜치·빌드·작업 규칙

**임찬영:** "규칙 제안합니다.
- **저장소:** GitHub 단일 리포, `main`(항상 배포 가능) / `dev`(통합) / `feat/*`(기능)
- **머지 규칙:** feat → dev는 1인 리뷰 필수, dev → main은 주간 빌드일(D+5/+10/+15)에만, 리드 승인
- **파일 구조:** `/src/core`(상태 머신·루프) `/src/systems`(detection, torpedo, depthcharge...) `/src/render` `/src/audio` `/params/*.json`(기획 수치, 태현 님 직접 커밋 가능) `/tools`(계측·핫리로드)
- **커밋 규칙:** 게이트 관련 수치에 영향 주는 커밋은 메시지에 `[G1]`~`[G9]` 태그 — 나중에 게이트 리뷰에서 '언제 뭐가 바뀌어 fps가 떨어졌나' 역추적용
- **금지:** main 직접 푸시, 파라미터 하드코딩(3차 결의), 빌드 깨진 채 퇴근"

**오세진:** *(반대)* "'빌드 깨진 채 퇴근 금지'는 15일 일정에서 독입니다. 큰 기능 절반 만든 날은 깨진 상태로 끊는 게 정상이에요. 그 규칙이면 다들 머지를 미루다가 금요일에 지옥이 옵니다."

**임찬영:** "정정하죠 — 금지 대상은 '**dev 브랜치**가 깨진 채 퇴근'. feat 브랜치는 얼마든지 깨져도 됩니다. 절반짜리는 feat에 두고 dev에 안 올리면 되는 거니까."

**오세진:** "그 정의면 동의합니다."

**서지우 (배석 발언):** "기획 쪽 접점 하나만 — 태현 님이 `/params`에 직접 커밋하는 건 좋은데, 수치 변경도 `[G7]` 같은 태그를 달게 기획팀에 전파하겠습니다. 튜닝표의 '테스트 결과' 열과 커밋 로그가 맞물리게."

> **결의 4:** 3브랜치 전략 / dev 무결성 규칙(feat는 자유) / params 기획 직접 커밋 + 게이트 태그 / 주간 빌드일에만 main 머지

## 안건 5. '처음부터 만들지 않는 것' 재확인 및 리스크 합의

**정하늘:** "3차 대회의 컷 테이블을 개발 언어로 재확인합니다. 아래 6개는 **코드에 자리(스텁)도 만들지 않습니다.** '나중에 넣기 쉽게 미리 구조만'도 금지 — 그 '미리'가 공수를 먹습니다.

강화 카드 / 승무원 이동 애니메이션 / 구축함 격침 / 자동 조준·페이드아웃 / 복잡한 카메라 흔들림 / 어군·장식 오브젝트

일정이 남으면 아래(6번)부터 역순 부활 — 어군·장식이 가장 먼저 돌아오고, 강화 카드가 가장 마지막입니다."

**남유리:** "하나만 예외 신청합니다. 어군은 스텁 금지에 동의하는데, **인스턴싱 렌더 경로**는 파문 이펙트에도 쓰는 공용 기술이라 어차피 만듭니다. 어군 '콘텐츠'는 안 만들되 '기술'은 파문용으로 존재한다 — 이 구분만 기록해주세요. 나중에 부활시킬 때 하루가 아니라 두 시간이 됩니다."

**정하늘:** "공용 기술은 컷 대상이 아니죠. 기록합니다. 마지막으로 리스크 3개, 대응까지 합의하고 끝냅니다.

- **R-D1. X-ray 스파이크 실패** (1주차 말 판정) → 아이콘 점멸 대체, 세진 이관 0.5일 (안건 3에서 확정)
- **R-D2. 수치표 D+3 지연** → 개발이 임시 기본값으로 선진행하되, 그 임시값 책임은 개발이 아니라 지연 쪽에 있음을 명시. 튜닝 일정만 뒤로 밀림
- **R-D3. D9에 코어 루프 미완** → 즉시 디렉터 보고, 3단계(은신) 범위를 '소음+눈 아이콘'만으로 축소하는 비상 컷 발동. 발동 권한은 리드 단독"

**전원:** 이견 없음.

> **결의 5:** 컷 6종은 스텁조차 금지 / 공용 기술(인스턴싱)은 예외 기록 / 리스크 3종 대응 경로 사전 확정, R-D3 비상 컷은 리드 단독 권한
